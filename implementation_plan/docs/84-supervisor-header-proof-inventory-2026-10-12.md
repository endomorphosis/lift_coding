# Durable proof inventories and numerical admission readiness

The qualified header producer can retain an independently admitted key/receipt
population in its original sealed SQLite owner and restore it through explicit
current host inputs. This closes a durable restart gap after the
[typed Terminal admission phase](83-supervisor-terminal-header-admissions-2026-10-12.md).
The inventory preserves custody, with all proof/completion/execution/publication
authority flags false. It does not establish live coverage or token savings.

The closed manifest retains signed task/repository/source-scope identities,
both independently admitted owner-path digests, sorted key/expected generic
receipt entries, exact original custody references and current bridge/codec/
inventory implementation digests. It supports explicit empty populations, at most
32 entries and 256 KiB of canonical inventory bytes. Original preparation/source
bodies remain in their existing custody records rather than being duplicated.

Persistence joins exact existing admissions, scoped analysis, Hammer/store and
Gate/cache against the full independently expected population, checks current
native custody and appends/reloads in the same owner. It performs no kernel replay
or generic positive-cache write; native denial bookkeeping may write control state.
The host retains the exact reference and independently expected inventory CID.
There is no owner discovery, replacement factory, cache enumeration or latest-row
selection. Store identity contains a basename, so CID/store IDs cannot replace
independent physical-owner path admission and current file/object fences.

Loading requires independently rebuilt complete preparations and explicit current
profiles, both trusted executable pins, bounds, expected inventory/task/scope and
both owner-path digests. It preflights the whole source/key/custody/lineage/version
population before the first kernel replay. Merely loading historical sealed native
proof records constructs no generic accepted evidence. It then imports each entry
with fresh native kernel replay and the independently expected generic receipt ID,
which is checked before that entry's positive `Gate.put`.

A later source/custody/population/version mismatch found by preflight prevents
the first replay. A syntactically valid but incorrect generic receipt CID is
known to be wrong after fresh replay; earlier valid entries may already have
written their correct receipts. The failed entry never puts its mismatched
receipt, and the loader returns no accepted population. Original references,
both owners, seal-key continuity, source, scope, profiles, bounds and complete
canonical preparations remain checked around callbacks and final return.
Validation remains sequential, without an atomic lease or rollback guarantee.

Supply restored handles with the retained independent population through the
existing Terminal host, using the same scoped analysis object as the rebuilt
preparations. Current render/commit and entry/exit checks remain required. Emitter
upgrades can change generic receipt IDs under unchanged native keys; version
profile/key/native custody and inventory provenance explicitly rather than hiding
equivocation or overwriting expectations. Requested limits do not certify OS
enforcement, and record caps do not bound lineage-prefix work or executable effects.

The numerical route needs a separate next step. The audited `largest-eigenval`
recipe retains 13 conditional Z3 checks and 22 finite numerical fixtures. It lacks
a reviewed native theorem/lowering, source-to-formal correspondence, independent

The [numerical guide](https://github.com/endomorphosis/ipfs_accelerate_py/blob/1f6d998a92db4024f35b57bbdb183a6626a7fa31/docs/agent_supervisor/numerical_proof_admission_readiness.md)
and [independent source audit](../../artifacts/supervisor-header-proof-inventory-20261012/numerical-readiness-source-audit.json)
specify the following implementation order:

1. Retain a bounded, typed non-authoritative qualification record for planning and
   retrieval. Preserve canonical SMT problem preimages, actual solver/result
   identities, numerical probe/population/process evidence, exact numeric encoding,
   task/source/profile bindings, assumptions and unresolved obligations.
2. Review an exact conditional theorem/lowering and source adapter. A source hash
   associates a recipe with observations; it does not prove Python/backend
   correspondence. Keep that assumption explicit if it remains undischarged.
3. Run an actual independent pinned kernel, retain proof/certificate and concrete
   execution/toolchain/dependency inputs, build complete non-placeholder keys and
   seal original lineage/key preparation. Require fresh replay after restart.
4. Qualify a separate spectral scoped-receipt bridge, preserving typed assumptions,
   residuals and native namespaces. Kernel assurance for an ideal lemma does not
   establish LAPACK/IEEE, all-matrix behavior, speed or whole-task completion.
5. Review a producer-aware Terminal interface or explicit spectral lane. Exact
   header handles, a boolean currentness callback or report hashes cannot substitute
   for the spectral producer's real bound guard and independently expected receipts.
6. Admit actual eligible task inventories, measure accepted/repeated-status
   populations and full native lookup costs, qualify bounded expansion, then
   census complete coding inputs before matched total native planning/coding/
   lookup/repair-token and official-reward trials. Keep failed attempts and unknown
   usage visible. Required facts remain inline until expansion qualifies.

The existing runtime source inventory includes the new loader. Rebuild and qualify
a current runtime archive before a live trial; historical archives remain
historical evidence. Observational DuckDB/Quack/DuckLake indexes can reference
the records without becoming positive proof authority.

Original embeddings and decoder checkpoints are reused. LegalIR, SecurityIR,
CodebaseIR and IntentIR remain separate by family/schema/version/decoder task,
with parallel 8D/384D/768D paths. This phase performs no model inference, training,
embedding recomputation, Hugging Face upload or live benchmark.
