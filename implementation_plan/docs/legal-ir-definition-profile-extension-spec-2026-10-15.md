## First implementation slice: V2 definition candidates

Implement these steps in order, with authored engineering fixtures. Genuine legal/formal reviews are required for later qualification, but explicit unreviewed caller declarations may be compiled into candidate records while those reviews are pending.

1. **Validate V2 custody before interpreting it.** Accept independently pinned original HTML, acquisition descriptor, complete V2 view report and sampling report. Replay the existing V2 view/sampling validators. Check full canonical report hashes separately from raw JSON file hashes. Original selected unit, whole-block occurrence and context references must match that exact sampler population. Derive any additional head/cue/body-atom subspan occurrences through `corpus_source` against the same pinned V2 source version and normalized view; bind their enclosing contributor/intersection references and their own exact contexts. These new occurrences are separate from the original sampler population. Never copy a legacy paragraph index into a V2 block index.
2. **Declare an exact meaning unit and scope evidence.** The caller supplies ordered definition contributors and their exact origins, a head/cue selection, an explicit Boolean body and scope/applicability evidence. Keep source-order custody separate from the caller's Boolean operand order. Keep whole contributor blocks and all original context requirements even when an atom uses a substring. A paragraph can contain several assertions; a definition can require several paragraphs. A cue inventory supplies no attachment or operator decision.
3. **Compile the bounded unary declaration.** Introduce a versioned V2 request/report path and reuse the current unary Boolean lowering. The initial supported operator is explicitly declared equivalence with an exact `means` cue, one Entity carrier and unary predicates. Preserve the native AST and all symbol/variable bindings. Accept no inclusion-to-equivalence rewrite, unnamed residual qualifier, inferred legal sort or implicit referenced definition. Unsupported declarations remain explicit dispositions in the selected population.
4. **Build a definition-only candidate graph and companion.** Use existing node/edge owners for source version, occurrences, declared scope, interpretation, definition assertion, head term sense, expression and issues. Emit `DEFINES`, source/provenance and scope edges. Omit norm nodes and `USES_DEFINITION` when no actual user has been supplied. Store the Boolean AST in the companion; ordinary graph connectivity is not a substitute for that AST. Every endpoint is a graph node record CID, not a payload CID or stable label.
5. **Prepare compatible review evidence.** Add a versioned V2 occurrence/context and definition-only subject path in the existing review adapters. Reuse the authentication and dependency engines. Bind the exact candidate profile, complete contexts, source bytes, AST, symbols and applicability declaration. The complete selected occurrence population includes whole contributors and every additional physical head/cue/body-atom or other role occurrence. Existing v1 definition-plus-norm signed claims cannot authorize the new subject by relabeling them. Blank §101 packet drafts and old 418-request source-queue histories are not valid substitutes for these inputs.

The first deliverable is therefore a replayable unreviewed V2 definition candidate with a complete companion, graph, open-context evidence and meaningful rejection tests. It is not a reviewed statutory definition, a connected norm component or a Lean release.
