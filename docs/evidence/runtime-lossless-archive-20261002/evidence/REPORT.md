# Runtime archive space-recovery experiment

The one zstd patch experiment is byte-exact but ineffective: 1,205,823,423 original bytes become a 1,167,170,658-byte patch, saving only 38,652,765 bytes (36.86 MiB; 3.2055%). The retained v4 reference would also remain required. No original archive was removed or replaced, and no admission policy changed.

Compression took 3.627 s with sampled child peak RSS 2,513,891,328 bytes. Successful streamed reconstruction took 1.933 s with peak RSS 1,478,963,200 bytes and emitted exactly 1,205,823,423 bytes. Its SHA256 equals the original and manifest: `edd48c6c80a88b06fce9a7fc3dfd01a1f9799552fc72f340aea5256f915f5dbe`. Native shared scheduler admission used 2 CPU slots, 4096 MiB, and one child slot; leases are released and children reaped. Each child had 4 GiB address-space, 1536 MiB file-output and 240 s CPU limits; each experiment had a 300 s wall limit. Resource costs include zstd children; parent stream hashing CPU is not included in child CPU figures.

The first read-only census found no observed process references in cwd/open files/maps, but permissions prevented 79 own-UID inspections and additional other-user inspections. This is not proof of inactivity. The first attempt retained that preflight refusal. A second attempt compressed successfully but decode refused its implicit window; a third attempt retained the same refusal. Final verification placed `--long=31 --memory=2048MB` after `--patch-from` and passed. These failures and exact commands remain retained.

The generated patch was experimental scratch. After exact reconstruction passed and all hashes/commands were retained, only this new patch was removed, recovering its 1,167,175,680 allocated bytes. Originals remain intact; this experiment therefore leaves only small reports/scripts/logs. The patch can be regenerated by the recorded compression command; `scratch-cleanup.json` records the exact removed scratch identity.

## Better candidate and next bounded experiment

Manifest-only inspection found 26,858 entries with equal path, hash and length across all 11 selected bundles, totaling 3,765,373,238 uncompressed bytes. The 11 gzip archives total 13,265,232,848 bytes. v4 and v5 differ in only one 11,452-byte source file. These are recorded manifest comparisons, not independently extracted member hashes or a measured CAS space saving.

The current archive producer `terminal_deployment.py:633` uses gzip level 1 and canonical tar member uid/gid/name/mtime/mode. Tar traversal order and Python's PAX/hardlink behavior also affect exact bytes. Gzip header timestamp remains nondeterministic; raw headers show filename `runtime.tar` and different timestamps, and must be retained. Current Python3.12.3 uses zlib1.3.

Proposed next experiment (not run): native-admitted streaming decompress/recompress of ONE original archive into SHA256, preserving its exact gzip header and trailer, using raw DEFLATE level1. Declare 1CPU/512MiB/1child, 300s wall, 30s admission wait, maximum4GiB decompressed stream, at most1MiB reports and no expanded tar file. Require exact original compressed size/SHA256. If that succeeds, propose a second bounded canonical member-CAS experiment: retain exact ordered raw tar headers/PAX/link records, data padding and final zero records, plus compressed CAS payloads keyed by freshly checked hashes; reconstruct one whole archive and require original SHA256 before any removal. This avoids assuming that regenerated tar metadata or current original checkouts match historical archives. Entry-level dedup may save enough space, but its savings remain unmeasured.
