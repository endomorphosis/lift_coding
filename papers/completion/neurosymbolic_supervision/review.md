## Evidence gaps and unsupported extensions

1. **Core effectiveness is unmeasured.** Section 8 (pp. 7–8) specifies tasks, metrics, controls, and statistics, but supplies no live paired experiment. Table 5 (p. 8) reports 40 controlled tasks with 58.90% median *estimated* context reduction and 40 sealer transitions with 43.6161% reuse / 43.0539% *estimated* compute reduction. These are preliminary replay/planner observations, not accepted repair rates or actual token/prover savings. The corresponding checked-in compression report explicitly requires `no_model_receipts`, marks all 40 rows `production_eligible=false`, and excludes provider acceptance. The sealer summary has zero measured CPU/proof-size/timing rows. Both preliminary results should be reproduced or accurately attributed, then clearly separated from new measurements.

2. **Source-present, integrated, and deployed are different claims.** Sections 1 and 9.1 (pp. 1–2, 9), §H.2 (p. 20), and §K.2 (p. 25) require a frozen loaded repository forest, not three unrelated repository heads. The workspace contains multiple copies of the packages under `external/` and `hallucinate_app/`. Record actual import paths, gitlinks, commits, overlays, dependency and native-binary identities, and runtime configuration. The PDF's named `ProcedureCegis`, `CompositionEdge`, bounded QF_LIA CEGAR adapter, and incremental SMT wrapper were not located by name in the inspected `external/ipfs_accelerate` / `external/ipfs_datasets` source trees. This is a provenance question: locate the claimed worktree/module or qualify the claims as missing/specification-only; it is not evidence that such code never existed.

3. **The provider positive path is a central qualification gap.** Section 4.2 (p. 4, lines 114–122) correctly says a zero local hook count is not a workflow-level saving and a candidate's `closes_claim` flag is not proof. Qualification must use the actual kernel caller, current plan/doctor/obligation evidence, and a genuine provider adapter; pair valid residual dispatch with minimally altered mismatches. Deterministic success also needs independent downstream validation. Deny-all is a diagnostic control, not a competitive repair baseline.

4. **Formalization losses can invalidate higher-level conclusions.** Sections 3.2 and I.1 (pp. 3, 22) explicitly identify modal erasure and conjunction approximations. Construct source states/traces differing on obligation/temporal semantics but sharing the projection; show that the actual admission path rejects unjustified source-level lifting. §B.2 (p. 13) requests duplicate assertion IDs, exact formula-root binding, stale fingerprints, unsupported terms, and unvalidated solver results. §I.2 and §L.2 (pp. 22, 25–26) add consistency, reachability, opaque clauses, and independently checked cycle closure. Distinguish assertion replay from retained-clause incrementality and solver UNSAT from kernel-checked proof. No retained-state speedup is currently established.

5. **Phase-aware reuse is a protocol awaiting end-to-end evidence.** Sections 6.2–6.3 and Appendix C (pp. 6, 13–14) require collection, fixture definitions, materialized instance commitments, execution keys, and setup/call/teardown outcomes. Include autouse/transitive fixtures, parametrization, finalizers, plugins/hooks, xdist ownership, dependency injection, clocks/RNG, and external snapshots. Equal incomplete hashes are insufficient. Reuse must retain required lifecycle effects and treat a teardown failure as whole-item failure. Show true reuse of unchanged obligations as well as rejection after each relevant mutation. A separately run cold oracle must independently score every retained reuse claim; runtime traces alone cannot establish closure.

6. **Publication and crash recovery are not proved by a local CAS API.** Sections 7.1–7.4, Appendix A.1, and §§C.3/F.4 (pp. 6–7, 11–14, 18) require complete mandatory inventories, exact parent/generation binding, persist-before-reference, current evidence, fencing, and reconciliation with operational state. Exercise missing/duplicated units, stale writers, failed CAS, duplicate/reordered events, crashes before/after persistence and publication, restart, and unknown provider outcomes. Compare sequential and parallel bytes, roots, and dispositions at multiple worker counts. Include a valid continuation after each recoverable fault, not just rejection.

7. **Native ZK is optional and has narrower semantics than test execution.** Sections 6.1 and J (pp. 5, 23–24) distinguish the opt-in Rust Groth16 adapter, a restricted atoms/implications derivation helper, runner attestations, and direct execution proofs. Table 16 names required adversarial changes to public inputs/outer metadata, keys/profiles/revocation, mandatory test inventory, and phase outcomes. Qualify a real named circuit, key policy, verifier, and timings if retained; otherwise record unavailable/untested and remove performance/deployment claims. Do not replace a missing native prover with simulated proof-shaped records. No reproduced exploitable attack is established by this review or the draft.

8. **World/procedure/refactoring extensions greatly exceed the evaluated core.** Sections 5.3 and 7.4; Appendices D–H (pp. 5, 7, 15–21) include synthesis, anti-unification, program-state prediction, learned graph models, logical datasets, VFS outboxes, architecture partitions, semantic remodularization, and federation. The draft itself preserves an earlier no-go on learned artifacts (§D.5.3, p. 16), describes refactoring work as separate (§E.4, p. 17), and calls typed-attention models optional (§H.3.2, p. 21). A retained benefit claim requires family/time holdouts, static/history/lexical/embedding controls, applicability/recall/calibration/abstention, independent replay/repair value, and actual result consumption. A source inventory or sidecar log is insufficient. Explicitly defer unevaluated extensions instead of launching all W1–W4 programs as submission prerequisites.

9. **The proofs are conditional specifications.** §7.3, §I.3, and Algorithm 1 (pp. 7, 22–23, 27) provide a design invariant, proof sketch, dependency-projection condition, and intended composition. They do not establish universal Python correctness or enforcement by the current code. State the initial-state, complete-manifest, translation/checker, publication exclusivity, deterministic observation/effect, and protected-authority assumptions. Map each assumption to an implementation gate or declared limitation. The illustrative full cycle in Appendix A (p. 11) uses schematic IDs and needs a genuine bounded run if it is promoted into a result.

10. **Costs and uncertainty need measurement and full denominators.** Sections 8.2–8.3 and G (pp. 7–8, 19–20) require accepted tasks per fixed budget, false acceptance/denial, solve rate conditional on dispatch, useful-progress latency, replanning latency/churn, fallback, and human time. Log provider calls/input/output/cached tokens and actual charges; CPU/GPU/memory/storage; setup/call/teardown; proof/checking; recovery; indexing/training/setup amortization. Use measured elapsed wall time rather than adding overlapping stages. Keep failed, timed-out, abstained, unavailable, and unsolved tasks in their declared denominators. Preregister a noninferiority margin and minimum useful-progress threshold before final runs; report uncertainty and finite-sample limitations even when observed failures are zero.

- Add one-factor comparisons for translation checking, symbolic routing, context selection, test/proof reuse, parallel preparation, and procedures if retained. Evaluate deliberately disabled admission checks only in an isolated adversarial harness with publication disabled. Use the same scoring oracle across conditions.
- Pair positive and negative cases at all six Table 18 boundaries. Use cold full validation as the reuse reference; compare sequential/parallel sealing; include cold/warm conditions and interrupted/restarted runs. Record the evidence identifier that actually changed the next route or accepted transition.
- Pilot on a separate development subset, repair harness problems, and freeze protocol/version before the final run. Choose final population size/repetitions using feasibility and a documented uncertainty/power rationale; do not select the task set because it gives favorable savings.
- Independently score main runs and ablations, generate tables directly from immutable per-task receipts, and retain failure examples and inconclusive results. A failed scientific hypothesis can produce an honest completed paper; it cannot be represented as a positive result.
