# Law-to-Action generated-code development runner

This increment implements an actual generated-response-to-handler path and
qualifies it with explicitly constructed development responses. It is the
engineering successor to the withdrawn LA-016 attempt. It does not supply
model-generated benchmark results, replace the planned 900 cells, or change
the final manuscript or any historical receipt.

## What runs

`loop.py` preserves each transport request, raw response, candidate, iteration,
feedback message and cost. A candidate is a JSON response containing a Python
program. The exact program bytes are hashed before native fact extraction and
checked again before execution. `native_candidate.py` accepts one
`run(payload)` function containing one to four direct calls to `allowed_sink`
or `other_sink`. All other syntax is rejected, including imports, attributes,
dynamic calls, decorators, annotations and Python 3.12 generic parameters.
This deliberately small language is a development qualification profile. The
full scientific tasks will require a separately reviewed program/handler
profile; these two sink names cannot stand in for the original study.

The trusted adapter supplies policy independently of candidate facts. Native
code-security extraction and request correlation are retained as evidence;
they are not treated as whole-program effect verification. The strict syntax
profile separately binds calls to real bounded handlers. A4 uses actual native
policy and Ed25519/UCAN checking, a SymPy satisfiability check with an independent
truth-table checker, byte/context-bound native decision receipts, explicit
pre-invocation enforcement, and a file-backed DuckDB consumption store. This
is a bounded policy check, not a Lean proof or a general CVE/IntentIR verifier.
Independent filesystem bytes and journal reconciliation determine useful work
and forbidden effects. Model claims of success are never an outcome oracle.

A0 receives task instructions; A1 adds policy; A2 adds permitted public source
context. A3 and A4 receive the same model context as A2 and add their actual
execution mechanisms. Constructed responses verify message composition only;
they provide no evidence about prompt or retrieval effectiveness.

## Resource boundary and retained evidence

`container_runner.py` reuses the unchanged LA-029 controller in `vendor/` for
actual Docker/cgroup controls. It explicitly uses the original rootful daemon
`unix:///var/run/docker.sock` and image digest recorded in
`development_runtime.json`. Each candidate has one CPU, 2 GiB memory, no extra
swap, 16 processes, no network, a read-only root filesystem, and 20 seconds of
wall/descendant CPU allowance. It receives only declared read-only mounts and
private writable output/consumption directories. Exact-owned child cleanup
and a retained empty parent cgroup prove termination and preserve complete
descendant CPU and peak memory counters. Unknown cleanup, effects or costs
remain unknown and stop the attempt.

The first image discovery accidentally inspected the default rootless daemon.
`qualification_attempt01` and `qualification_attempt02` preserve the two
resulting pre-start create failures. No candidate or model ran in those
attempts. `qualification_attempt03` preserves the corrected positive A4 probe;
`development_qualification_v1` preserves the first complete boundary
qualification. Later versions include fixes and source snapshots instead of
rewriting those records.

`development_qualification_v2` stopped on a native watchdog
`resource_observation_OSError` while the fourth candidate's leaf cgroup was
being torn down. The candidate exited with status zero and its retained parent
proved whole-group exit and exact-owned cleanup, but the qualification remains
failed and its effect disposition remains unknown. Version 3 is a fresh
development qualification after that explicit reconciliation, not a changed
scientific denominator or an upgraded v2 admission flag. The original watchdog
source remains unchanged; qualification of its teardown-observation behavior
belongs to the full scientific runtime work.

## Development acceptance

The canonical qualification is `development_qualification_v3`. It covers:

1. A0 actually creates the undeclared file, establishing observer sensitivity.
2. A4 performs the permitted useful export.
3. A4 refuses the undeclared candidate before delegation, sends its observed
   failure back to the next iteration, and executes a repaired permitted
   candidate without a forbidden effect in either iteration.
4. A Python generic-function candidate is rejected without a handler effect.
5. A3 performs the permitted export using the actual lightweight policy/UCAN.

These are five controls and six actual contained candidate executions, with
zero model calls and 8.932969 measured descendant CPU seconds in version 3.
`development_cost_summary.json` separately accounts for all 19 historical cell
envelopes, including the two pre-start failures, the positive probe, earlier
qualification and failed version 2. Known descendant CPU totals 28.239412
seconds; the two pre-start envelopes retain unknown counters. Separate
interface fault injections check that failed
inference reservations still consume a call, token usage remains unknown when
unavailable, uncertain execution cannot be reported as absence of effects,
and unqualified scientific dispatch is refused. Those fault injections do not
call a provider or create a container.

## Remaining scientific qualifications

`QualifiedLocalHTTPTransport` is a pluggable local transport, not a model
launcher. It requires an already loaded, separately qualified model service
and hash-bound actual model/deployment/tokenizer/chat-template configuration.
It never starts a service or downloads weights. A model profile alone cannot
admit a source: `StudyAdmission` additionally requires an actual development
report, exact current code/runtime/prompt bindings, separate runtime and cohort
audits, and the original complete schedule. No such scientific admission or
model qualification has been created by this increment.

The original scientific contract remains 30 lineage-disjoint families and 60
paired cases (6 legal, 12 CVE, 12 skill families), population-specific
development/calibration/final quotas, the original ranked-split salt,
A0–A4 × seeds 104729/104759/104761, and 900 cells including 540 final cells.
Each attempt retains its original maximum of eight calls, 2048 input and 1024
output tokens per call, and 120 wall seconds. Missing evidence keeps the
original denominator unrun.

Still required before that study: lawful exact source pins and normalized-text
and ancestry leakage audits; source-relative tasks and independent effect
oracles; a scientifically adequate qualified code/handler profile; full
runtime/dependency provenance; actual model tokenization/decoding and service
resource qualification; a durable complete schedule/resume/reconciliation
driver; and complete hard-deadline accounting for the whole attempt including
cleanup. Real inference and final-cohort release require those concrete
qualifications. Outside human annotations are not required for the established
automated policy-relative scope; legal validity and human semantic-fidelity
claims remain outside its evidence.

The native successor contracts are `LA-030.task.json` for this development
increment and `LA-031.task.json` for the still-unfinished actual scientific
work. LA-031 requires real model generation, the original full cohort and
schedule, analysis and the manuscript update. Completing LA-030 does not
complete LA-G5 or LA-031.
