# Add JWT Authentication Endpoints to a Django Project (django-jwt-auth)

## Background
`django-jwt-auth` provides JSON Web Token (JWT) authentication support for Django, using PyJWT under the hood. It exposes Django REST Framework-style endpoints for obtaining and refreshing tokens, and supports common JWT configuration such as algorithm, expiration, refresh windows, and Authorization header prefix.

## Use Cases
- Add a token-based auth mechanism to a Django API.
- Issue JWTs to clients via a username/password login endpoint.
- Refresh JWTs (optionally) to extend session continuity.
- Configure token expiry, verification behavior, and auth header prefix.

## Inputs
- A Django project with URL routing.
- A user account (username/password) for testing token issuance.
- Ability to set Django settings values (e.g., JWT_* settings).

## Outputs
- `/api-token-auth/` endpoint that returns a JWT on valid credentials.
- `/api-token-refresh/` endpoint that refreshes a JWT (when enabled).
- Ability to call protected endpoints using `Authorization: Bearer <token>`.

## Steps
1. Install the package:
   - `pip install django-jwt-auth`
2. In your Django `urls.py`, import the JWT views:
   - `from rest_framework_jwt.views import obtain_jwt_token, refresh_jwt_token`
3. Add URL routes for token obtain and refresh:
   - `url(r'api-token-auth/', obtain_jwt_token)`
   - `url(r'api-token-refresh/', refresh_jwt_token)`
4. Ensure you have a Django user to test with (a username/password you can submit to the auth endpoint).
5. Obtain a token by POSTing JSON credentials to `/api-token-auth/`.
6. For any protected API URL, send the token in the `Authorization` header using the configured prefix (default: `Bearer`).
7. (Optional) Enable refresh capability by setting `JWT_ALLOW_REFRESH = True` so issued tokens include `orig_iat`.
8. (Optional) Adjust expiration by setting `JWT_EXPIRATION_DELTA` (default: 300 seconds).
9. (Optional) Adjust refresh window by setting `JWT_REFRESH_EXPIRATION_DELTA` (default: 7 days).
10. (Optional) Adjust verification behavior with `JWT_VERIFY` and `JWT_VERIFY_EXPIRATION`.
11. (Optional) Change the auth header prefix with `JWT_AUTH_HEADER_PREFIX` (default: `Bearer`).
12. (Optional) Use RS* algorithms by setting `JWT_ALGORITHM` to RS256/RS384/RS512 and providing appropriate RSA keys to encode/decode.

## Verification
Run these checks against a locally running Django server (example uses `localhost:8000`) and a known user.

```bash
set -euo pipefail

BASE_URL="http://localhost:8000"
USERNAME="admin"
PASSWORD="abc123"

# 1) Obtain a token; expected: response JSON contains a non-empty "token" field.
TOKEN="$(
  curl -sS -X POST -H "Content-Type: application/json" \
    -d '{"username":"'"$USERNAME"'","password":"'"$PASSWORD"'"}' \
    "$BASE_URL/api-token-auth/" \
  | python -c 'import sys, json; print(json.load(sys.stdin)["token"])'
)"

python - <<'PY'
import os
assert os.environ.get('TOKEN'), "Expected TOKEN to be non-empty"
print("Token acquired (non-empty).")  # expected: prints confirmation
PY

# 2) Call a protected endpoint with the Authorization header.
# Expected: request succeeds for your protected endpoint (commonly HTTP 200).
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE_URL/protected-url/" > /dev/null

# If the curl command exits successfully, the header format and token are accepted.
echo "Protected endpoint call succeeded."  # expected: prints this line
```

## Safety
- Keep `JWT_SECRET_KEY` safe and private; by default it uses `settings.SECRET_KEY`.
- Disabling `JWT_VERIFY` or `JWT_VERIFY_EXPIRATION` reduces security; only do so with a clear, justified reason.
- Use short expirations (`JWT_EXPIRATION_DELTA`) appropriate to your threat model; refresh (`JWT_ALLOW_REFRESH`) extends session lifetime and should be controlled.
- If using RS* algorithms, ensure correct handling and protection of private/public keys.
