# Deploy S3 Reverse Proxy with OpenID Connect and Basic Auth (oxyno-zeta/s3-proxy)

## Background
s3-proxy is a reverse proxy in front of one or more S3 buckets that supports GET, PUT, and DELETE, with authentication via OpenID Connect (OIDC) and/or Basic Auth. It can mount buckets by hostname and path, apply auth rules per path and HTTP method, and expose Prometheus metrics.

## Use Cases
- Protect S3-hosted content behind OIDC login (one or multiple providers).
- Publish (PUT) and delete (DELETE) objects in S3 through a controlled proxy.
- Front multiple buckets with a single entrypoint and route by hostname/path.
- Add Basic Auth as a lightweight access control option.

## Inputs
- One or more S3 buckets to proxy.
- (Optional) OIDC provider configuration (single or multiple providers).
- (Optional) Basic Auth credentials (single or multiple accounts).
- Desired bucket mount rules (hostname and/or path mapping).
- Authorization rules by bucket/path/HTTP method (e.g., allow GET, require auth for PUT/DELETE).

## Outputs
- A running reverse proxy that serves S3 objects over HTTP(S) with:
  - GET/PUT/DELETE support
  - OIDC and/or Basic Auth protection
  - Optional redirect to original host/path after OIDC authentication
  - Prometheus metrics endpoint

## Steps
1. Open the project repository and documentation:
   - Repo: <URL>
   - Docs: <URL>
2. Decide which authentication mode(s) you will enable:
   - Basic Authentication (supports multiple accounts)
   - OpenID Connect (supports multiple providers)
3. Define your bucket routing/mount strategy:
   - Map buckets by hostname and/or multiple paths
   - Plan which paths should behave as an “index document” vs listing behavior
4. Define authorization policy per bucket/path and HTTP method:
   - Example pattern: allow unauthenticated GET for public reads, require auth for PUT/DELETE
5. Choose your deployment packaging:
   - Container image (available on Docker Hub: oxynozeta/s3-proxy)
   - Or build from source (Go project; see repo)
6. Create your runtime configuration according to the official documentation:
   - Configure S3 endpoints (including custom S3 endpoints if needed)
   - Configure buckets, mount points, and method/path auth rules
   - Configure OIDC providers and redirect behavior (if using OIDC)
   - Configure Basic Auth users (if using Basic Auth)
7. Deploy the proxy in your environment (local, VM, Kubernetes, etc.) using your chosen packaging, and expose an HTTP endpoint.
8. Enable and scrape Prometheus metrics if you need operational visibility.
9. Validate read path behavior (GET) against a known object.
10. Validate write/delete behavior (PUT/DELETE) only for authorized identities.
11. If using OIDC, validate login flow and confirm it redirects back to the original host/path.
12. Document your bucket mappings and auth rules for operators (include which methods are permitted per path).

## Verification
Run a basic HTTP check against the deployed endpoint to confirm:
- The service is reachable
- A GET returns an HTTP status (200 for public objects; 401/302 if auth is enforced)

```bash
set -euo pipefail

# Set this to your deployed s3-proxy endpoint and an object path you expect to exist.
BASE_URL="http://localhost:8080"
OBJECT_PATH="/"

# This prints the HTTP status code for a GET request.
# Expected outcomes (depending on your configuration):
# - 200: object served without auth
# - 401: auth required (Basic Auth)
# - 302: redirect to OIDC provider for authentication
code=$(curl -sS -o /dev/null -w "%{http_code}" "${BASE_URL}${OBJECT_PATH}")
echo "HTTP status: ${code}"

case "$code" in
  200|401|302) echo "OK: service reachable and responding as expected";;
  *) echo "Unexpected status: $code"; exit 2;;
esac
```

## Safety
- Treat PUT/DELETE as high-risk operations: restrict them by path and method, and require authentication.
- Prefer OIDC for user access control; use Basic Auth carefully and rotate credentials.
- Validate bucket mount rules to avoid accidentally exposing unintended buckets/paths.
- If enabling public GET, review index document and listing behavior to prevent information disclosure.
