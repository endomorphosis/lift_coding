## Trust is an intervention contract, not a receipt flag

All arms use the same trusted controller, permitted effects and independent
acceptance authority. Trust weakening must never be an efficiency treatment.

| Evidence | What it permits | What it does not establish |
|---|---|---|
| Hash-bound source/capsule/body or unsigned candidate | Identity, reproduction, and nomination for checking | Successful execution, proof, authorized promotion, freshness without current-state checks |
| Native solver result within a declared fragment | The checked relation under pinned assumptions/backend | Arbitrary Python correctness, kernel reconstruction or authorization to publish |
| Development Ed25519 runner attestation | Reuse only after verification under the exact current signer/policy and recorded setup/call/teardown commitments | Generic tracing completeness or automatic production admission |
| Native procedure certificate plus independent current promotion authority | The explicitly permitted signed interpreter/registry path | A body store or applicability oracle merely because metadata was signed |
| Groth16 event-DAG proof | The implemented circuit relation under pinned key/binary/public statement | Truth of event records, pytest execution, or unique full archive-root bytes when the circuit commits only a scalar |

The reuse adapter's real signer issues only after actual cold setup/call/teardown
pass; keys stay outside candidate code. Its enrolled source/dependency/fixture
profile is intentionally closed. Snapshot fields are not a generic runtime
dependency tracer. Missing signatures, revoked policies, changed environment,
unknown fixture values or source changes cause cold validation. Required setup
and teardown always execute; teardown failure defeats whole-item success even
after call reuse.

Current procedure bodies remain unsigned development candidates executed by a
new bounded adapter. The native registry stores metadata and needs independent
certificates/promotion. Before claiming native signed execution, implement and
exercise that path with a separate development issuer and its negative cases.
Until then label the candidate mode explicitly and let independent validation
govern acceptance. A signature alone never promotes an incorrect procedure.

The available source-built Groth16 backend supports v1/v2/v3 and rejects v5.
Its v3 scalar-root alias requires exact expected full root/count and key/binary
binding at the caller. It cannot substitute for the missing pytest-attestation
profile. Keep proof-system relation claims separate from runner attestation and
from faster direct-hash or cold-check baselines.

## Finite next development cohort

The next integrated cohort has the four existing original-development repairs,
not four newly invented historical trajectories. Augment each with a **six-event
authored operational sequence on the real repository**. Exact event payloads,
mutation locations, expected outcomes and scoring permissions must be created
and frozen from public source before effects. They are not recruited data yet.

1. Bind the genuine public issue and compile an explicit plan/obligation set.
   Score plan coverage against independently authored criteria, distinguishing
   task authority from an inferred specification.
2. Attempt the genuine historical repair; seal each proposal before hidden
   scoring. Retain failures and all expenditure. The scorer-only process may
   open its existing independent oracle; the proposer and semantic preparation
   cannot read target patches or hidden tests.
3. Revisit the same obligations on unchanged accepted bytes. Allow every arm
   ordinary exact no-op detection; do not force a model call merely to make the
   baseline expensive. Measure what each arm actually recomputes or consumes.
4. Apply a frozen comment-only edit to a previously unchanged dependency, or the
   edited module when no separate dependency exists, and require revalidation.
   This tests source identity/invalidation on a real repository; it is not a
   second naturally occurring bug fix.
5. Apply a frozen configuration/environment or fixture change requiring current
   lifecycle resolution, with a corresponding public obligation. Choose the
   exact change using public-source development qualification and retain any
   cold failures. Do not count a guessed expected outcome as a hidden oracle.
6. Interrupt after validated candidate evidence but before publication, restart,
   and complete the current accepted transition. Include a distinct stale-parent
   branch that loses CAS and must replan. Both normal and losing continuations
   must have terminal records; failed or unknown external effects stay charged.

Events 3--6 are controlled augmentations, not new upstream repairs. If the
genuine repair fails, the sequence follows a frozen failure branch; it must not
secretly receive a reference patch to make later events look successful.
Source and outcome dependencies within a trajectory stay intact during analysis.

Primary arms, versioned separately from historical A/B labels:

| Arm | Context | Reasoning/action | Cross-event state and validation |
|---|---|---|---|
| A | Raw source with ordinary lexical retrieval | Competent conventional tool-using model baseline; common cheap no-op checks | Public execution history remains available; ordinary cold validation and durable effect/idempotency records |
| B | Source-preserving native semantic substitution; equal source-expansion access | Same caller policy and neural residual as A | Same conventional state/validation as A |
| C | B context | Actual checked symbolic analysis/synthesis before the common residual | Same conventional state/validation as B |
| D | C context and reasoning | Applicable procedure/world-memory suggestions consumed under current bindings | Persistent semantic state, qualified lifecycle reuse and governed publication/recovery |

D must name what procedure/world mechanism is actually implemented. A missing
mechanism remains an unrun comparison; it cannot be silently replaced by a
cached description. If the current candidate-only procedure mode is used, that
limitation remains part of D's profile and signed-native procedure efficacy
stays open.

Run both local-cold and local-warm profiles: cold starts with empty semantic,
procedure and proof caches; warm restores a hash-bound separately metered prime.
Every arm receives equal public history and information access. Include each
arm's actual prime/model/setup expenditure in fixed-horizon totals. Keep provider
prompt-cache fields separate: local warm state is not proof of provider cache
control. The ordinary effect ledger remains enabled in every arm, including
stateless controls, to prevent duplicate effects.

The primary finite matrix is **4 families × 4 arms × 2 local cache profiles =
32 trajectories / 192 event observations**. A prospectively fixed first tranche
is the first two development families under cold A--D: eight trajectories. It
tests whether the unified caller and telemetry work before the remaining frozen
cells proceed. Stop only for declared harness, custody or usage failures; do not
drop an arm because its savings are unfavorable. If code must change, retain the
old version/results and create a new development freeze.

For development mechanism attribution, schedule seven one-factor controls on
the same four families under the warm profile: B with additive rather than
substituted context; D without symbolic routing; D without reuse; D without
persistent semantic state; D without procedures; D with a fixed complete template
instead of synthesized procedures; and D without world memory. This adds
**28 trajectories / 168 events**, for **60 trajectories / 360 events** overall.
The template must be frozen before these outcomes. A package comparison cannot
identify the benefits of its constituent mechanisms.

A provisional feasibility ceiling is four provider calls per trajectory,
including prime, planning, formalization, source-expansion decisions, proposals,
reviews and recovery: at most 32 calls in the first tranche and 240 across the
entire development matrix. Every consumed call shares that budget; exhausting it
is a retained failure/abstention. The final executable freeze must choose model,
request parameters, byte/time caps and exact call identities before effects.
These are proposed ceilings, **not calls authorized or issued by this document**.
Choose them for feasibility, not as a claimed power calculation. If a realistic
workflow needs a different budget, amend the unrun development design before
effects and preserve its provenance.

## Endpoints and complete economics

Primary quality endpoints are independently valid repair, all required event
obligations satisfied, and successful complete trajectory/publication. Report
false admissions, abstentions, invalidation misses, repeated dispatches, rejected
stale work and valid continued work separately. The denominator includes every
scheduled task/event; record dependent downstream failures rather than deleting
them. Independent cold-oracle calls are evaluator overhead; actual mandatory
runtime validation stays charged to its arm.

Maintain a single append-only workflow ledger with family/trajectory/event IDs,
parent/source/obligation identities, arm/component decisions, call purpose,
provider request/response hashes, timestamps, process effect IDs, input/output/
cached/reasoning fields, authoritative provider total, API-reported charge and
settlement status. Preserve unknown usage as unknown. Never add overlapping
components or report cached-input tokens as avoided work.

For the fixed workload, compute `T_a = T_setup,a + sum(all provider totals)` and
report reduction relative to A only when telemetry is complete and quality
meets the prospectively declared margin. Also report tokens per independent
success (undefined when zero), cumulative expenditure over event horizons,
success-versus-budget, calls avoided by a witnessed closure, expansions, fallback
cost, setup/prime cost and empirical break-even. Show all failures. An arm that
abstains cheaply is not an efficiency win. Host CPU, wall time, storage,
prove/verify and human effort remain separate measured quantities.

This small development matrix yields descriptive paired observations. Do not
treat six events, repeated cache runs or concrete test inputs as independent
families. A later confirmatory analysis must cluster by repository/lineage and
preserve temporal dependence within trajectories.

## Genuine trajectory and confirmatory recruitment still required

Recruit new independent lineages outside the sixteen exposed families and
related-paper overlaps. Each accepted trajectory needs multiple genuine public
objectives on a consistent repository history, exact pre-event source snapshots,
independent scorer-only acceptance for each step, declared context/dependency
scope, public permissions and environment custody. A Git commit count, an issue
title or an unused-family name alone is not recruitment. A curator can qualify
hidden tests and references in a separate process; proposer/context/policy
developers must not inspect them. Keep all failures and explicit exclusion
reasons; never backfill after seeing model outcomes.

After the integrated development pilot, choose the number of independent
families from observed variance, intended precision, feasible cost and a
prespecified quality margin, then freeze recruitment, task-order/cache rules,
arms, budgets and stopping criteria before confirmatory outcomes. Do not call the
old sixteen-family target a power analysis. Natural multi-issue trajectories,
larger independent repairs, difficult unknown-frontier cases and learned
world/procedure holdouts must remain research obligations until executed.
